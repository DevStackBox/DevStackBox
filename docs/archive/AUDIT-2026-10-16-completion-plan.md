# DevStackBox completion audit and fix plan

Audit date: 16 October 2026. Repository version: 0.1.9. Baseline commit: `d96b453`.

This is a point-in-time engineering audit and proposed execution backlog. `docs/feature-status.mdx` remains the feature-status source of truth; update that file as fixes are verified. This audit does not certify the existing DONE labels.

## Conclusion and scope

The Windows PHP stack has substantial implementation across its main workspaces. The next milestone should be a reliable release candidate: reconcile configuration paths, protect backup/restore operations, finish exposed controls, and establish repeatable release validation before adding more features.

## User requirements confirmed after the audit

These requirements govern implementation and release acceptance, including where earlier roadmap language is weaker.

1. **Installed application is the product.** Validate the actual installer and installed executable, not just development mode. All supported features must work after installation on a clean Windows machine using packaged resources. No dependency on the source checkout, XAMPP, another stack, developer tools, or another application's PHP/MySQL/Apache. Optional downloads must be explicitly identified; everyday bundled-stack operation must work offline.
2. **Own the entire service lifecycle.** Resolve Apache, PHP/CGI, MySQL server and client tools, mysqldump, mysqladmin, and OpenSSL from the verified DevStackBox installation. Do not fall back to unrelated PATH executables. Status, start, stop, restart, database connections, backup/restore, terminal launchers, update and uninstall must consistently target this installation and its managed data/config. If an owned binary is missing, show an actionable repair error. If a port is occupied, report the conflict and offer supported configuration changes; never silently connect to or terminate another stack. Arbitrary commands users deliberately type in a general shell remain their choice; app-generated commands must resolve owned tools explicitly.
3. **Production-quality interactions and copy.** Audit all button labels, menus, tooltips, dialogs, installer text, errors and empty/loading states. Use clear consistent terminology and accurate outcomes. No placeholder controls, console-only actions, misleading Ready/Success states, debug copy, or unexplained raw errors. Destructive actions identify the affected resource; keyboard focus, disabled/busy states, progress and retry behavior are consistent.
4. **Only the user's DevStackBox branding.** Existing assets under `docs/images/logo/` are the branding source; do not invent/recolor the logo or add third-party brand marks. Use the supplied identity consistently in window/taskbar/tray, installer, shortcuts, About, onboarding and application chrome. The primary logo contains blue `#1656FC` and dark `#131B25`; derive UI tokens from approved assets, with theme-appropriate neutral surfaces. Remove arbitrary service-specific accent palettes and Apache/MySQL/PHP brand logos from the app UI under the user's instruction. Clarify whether neutral functional icons (search, settings, close, etc.) are permitted before icon replacement; retain text-based status meaning regardless of color.
5. **Windows desktop presentation.** Use a compact, resizable desktop workspace with consistent menus/toolbars, restrained borders/radii, Windows-appropriate typography, coherent pane scrolling, keyboard shortcuts and context menus. Avoid oversized marketing headings, repeated web cards, excessive whitespace, decorative animation and webpage-style stacking. Verify native titlebar/window controls, minimize/maximize/restore, tray behavior, DPI scaling and supported minimum window size. This requirement is about user experience; Tauri remains the existing implementation foundation.
6. **Complete light/dark/system themes.** Use shared semantic tokens for every screen, dialog, menu, status, focus/hover/disabled state, chart, editor, terminal and scrollbar. Preserve selection across launches; System mode must react while Windows appearance changes. Check logos against actual backgrounds, readable contrast and initial-render theme flash. Keep brand identity consistent in both themes.

Additional source evidence from this follow-up: service cards use `/apache.svg`, `/mysql.svg`, `/php.svg` and unrelated orange/blue/purple classes; `globals.css` contains generic grayscale primary tokens and unrelated chart colors. `theme-provider.tsx` reads `matchMedia` once per theme selection without subscribing to OS changes. `AppLogo` selects `logo-dark.svg` for dark mode, but that asset uses `#231F20` paths, requiring contrast review; do not assume the filename describes its intended background.

**Required acceptance additions:** test on a clean VM and on a VM with unrelated Apache/MySQL/PHP ahead of DevStackBox in PATH; record the executable paths, PIDs, data directory, config path and connected database identity. Run every supported workflow in the installed build. Capture and review every screen in light and dark modes at 100%, 125%, 150% and 200% DPI, including window resizing and live System-theme changes. Verify bundled branding in the installer, shortcuts, taskbar and tray. These are release gates, not optional polish.

Reviewed the desktop repository's routes, UI, command registry, Rust command implementations, runtime helpers, installer hooks, build scripts, documentation, and existing automated checks. The separate `devstackbox-website` repository, live website, GitHub settings/secrets, published installers, and remote release artifacts were not audited. No services were started/stopped and no user databases, Windows hosts entries, or certificates were changed. No product fixes were applied during this planning pass.

“Implemented” below means code exists and is connected at source level, not that every workflow passed desktop end-to-end testing. Browser mock mode cannot establish native functionality. Clean-machine installation, UI accessibility, privilege escalation, real database restores, and update recovery remain verification work.

## Execution plan and dependencies

Execute in this order; each phase should be delivered as small reviewable changes with regression coverage. Estimates below are relative size, not calendar commitments.

### Phase A - establish a repeatable baseline (small–medium)

- [ ] G15: path handling, Clippy, docs validator; choose one package manager/lockfile policy.
- [ ] G13: add CI for frontend tests/build, Rust tests/Clippy, docs validation and version consistency.
- [ ] G22: reconcile feature-status with this evidence; record explicit native tests still pending.

Exit: all baseline gates pass from the supported checkout layout and CI; failures are reproducible.

### Phase B - make current everyday workflows correct (medium–large)

- [ ] G04/G08: active PHP binary/config resolution, safe version download/switch, extension persistence.
- [ ] G05/G06/G07: validated config edits, restore history, local Monaco, dirty-state handling.
- [ ] G09/G17/G19: real shell behavior, correct runtime/connection environment, truthful PHP status, Composer decision, stable tabs.
- [ ] G11: safe transactional vhost and hosts-file operations.

Exit: create a local PHP site and database, toggle an extension, switch PHP, edit/restore config, use each supported terminal, and access phpMyAdmin at custom ports in the installed app. Failures preserve prior working state.

### Phase C - protect data and finish release safety (large)

- [ ] G01/G02/G03: reliable backup creation, preflight/restore recovery, external-root and large-data handling.
- [ ] G10/G16: protected credentials, sensitive backup policy, webview policy.
- [ ] G12/G14: updater state/preflight, verified shutdown and installation behavior.
- [ ] G13: reproducible complete NSIS package, release metadata/signature checks, synchronized versions.

Exit: interrupted backup/restore/update scenarios have demonstrated recovery; an old installed version upgrades without losing databases, sites, settings, SSL material, or selected PHP configuration. Phases B/C both block public release; isolated data-safety work can begin earlier.

### Phase D - complete product experience (medium)

- [ ] G18/G20/G21: log performance, SSL trust/vhost coverage, user grants, project navigation, translations and accessibility.
- [ ] Check every empty/loading/error/retry state and keyboard path, dark/light themes, 1366×768 and high-DPI layouts.
- [ ] Expand diagnostics only with useful, redacted support data.

Exit: no exposed action silently does nothing; unsupported features are clearly excluded; all supported screens are usable in EN/HI and with keyboard navigation.

### Phase E - release candidate verification (large, environment-dependent)

- [ ] Clean Windows 10/11 installs with no PHP/MySQL/Apache already available on PATH.
- [ ] Offline first launch with fresh webview/editor caches; resolve the WebView2 bootstrapper's network prerequisite or document it accurately.
- [ ] Standard user launch after administrator install; UAC accepted, rejected, and canceled.
- [ ] Ports occupied by IIS/XAMPP/other processes; verify unrelated processes remain untouched.
- [ ] Custom data-root override; supported install layout; spaces/non-ASCII user paths; low disk space and denied access.
- [ ] PHP HTTP/CLI parity; PHP switching; optional extension toggles; config history and invalid-config recovery.
- [ ] MySQL create/user permissions/import/export/root-password restart; large data and malformed SQL.
- [ ] Back up and restore into an isolated fixture, comparing file checksums and database content; include external vhost roots and interrupted operations.
- [ ] Upgrade from previous published version, failed/interrupted update, reinstall, uninstall with preserve/delete data choices.
- [ ] Check actual updater artifact signatures separately from Windows Authenticode signing; current config has no certificate thumbprint.
- [ ] Separate website audit: download target/version, setup instructions, screenshots, roadmap and feature claims match the tested release.

Exit: retain machine/setup details, test steps, expected/actual results, logs, artifact checksums and outstanding limitations in a release checklist. All P0/P1 findings must be closed or explicitly scoped out of the release with matching UI/docs.

## Scope boundary for “fully complete”

Use the existing Windows/Apache/PHP/MySQL/phpMyAdmin product vision as the v1 boundary. Composer support is useful and its current visible no-op needs resolution. WordPress/Laravel installers and project templates are separate optional milestones after reliability; Docker, Redis, PostgreSQL, Nginx and runtime managers stay outside the existing v1 scope.

A completion claim requires tested user journeys and reproducible installation/update/recovery. The existence of a page or command, a successful TypeScript build, or a numerical completion percentage is insufficient evidence.
